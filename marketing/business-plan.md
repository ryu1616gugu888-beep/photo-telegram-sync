## 1. プロダクト概要

iPhoneの「写真」アプリに新しく追加される写真・動画を、自動でTelegram(自分のBot宛)へ転送するiOSアプリ。
過去に自分のGoogle Photos(2万枚以上)をTelegramへ一括移行した実体験の知見を活かして開発。

## 2. ターゲット層

- Google Photosの無料枠終了・値上げに疲れている人
- iPhone/iCloudのストレージ容量アラートに悩まされている人
- 既にTelegramをヘビーに使っている人(乗り換えコストが低い)
- (二次的に)個人開発・iOS開発に関心がある層(開発の裏側コンテンツ経由)

## 3. 差別化ポイント

1. **Telegramは保存容量無制限。** iPhone本体・iCloudの空き容量を一切消費しない。
2. **開発者は写真もパスワードも一切預からない設計。** オンデバイス処理、Bot Token/APIキーは端末Keychainのみ。
3. **原本画質を保持する送信ロジック。** 写真はdocument形式、動画はvideo形式で使い分け、Telegram側の
   自動再圧縮を回避(実装・テスト済み)。
4. **実体験に基づく信頼性。** 2万枚超の一括移行という一次情報を持っている。
5. **IFTTT/Make等の汎用自動化サービスを経由しない。**(2026-09-06競合調査で追記)類似の「写真追加→
   Telegram送信」はIFTTT/Makeでも組めるが、それらは写真データが一度サードパーティのクラウドを経由する。
   本アプリは端末→Telegram間に他社サーバーを一切挟まない。また汎用連携では作り込まれていないと
   見られるdocument/video形式の使い分け(原本画質保持)も強み。

## 4. 現在のフェーズと収益化の考え方

- **配布方針(2026-09-06、方針転換): App Storeでのリリースは費用対効果が薄いと判断し、当面見送る。**
  代わりに (1) **GitHub上でソースコードを公開**(技術者が自分でXcodeビルドして使える形)、
  (2) **note等Web上でのコンテンツ発信**(開発ストーリー・短編動画・SNS投稿)の2本柱に絞る。
  個人のXcodeビルドのみ、という前回決定(2026-09-05)からの発展形であり、方向性は矛盾しない
  (「配らない」→「ソースを公開して各自ビルドしてもらう」への一歩前進)。
- marketing活動は引き続き「製品の即時販売」ではなく「ビルドインパブリックによるオーディエンス形成」が
  目的。note記事・短編動画・SNS投稿の「フォロー/続報待ち」型CTAに加えて、**GitHubリポジトリへの
  リンクを新たなCTAとして追加できる**(ダウンロードではなく「ソースを見る/自分でビルドする」導線)。
- **この方針転換によるトレードオフ**: GitHub公開は技術者・個人開発好きの層にしか実質的に届かない
  (一般の「Google Photos容量に疲れた人」はXcodeビルドをしない)。ターゲット層(2節)のうち、
  実際にリーチできるのは当面「個人開発・iOS開発に関心がある層」が主となる。
- 収益化の実現方法(App Store断念により、直接の課金・広告収益化は当面選択肢から外れる):
  - GitHub Sponsors / Buy Me a Coffeeなどの寄付・スポンサー形式
  - note記事自体の有料化(note標準機能、アプリと独立して収益化できる)
  - 個人ブランディング・ポートフォリオとしての間接的価値(将来の仕事・機会につながる)
- **今の目的**: 収益化モデルの確定を急がず、まず(a)動くものをGitHubで公開する、(b)ビルドインパブリック
  で信頼と関心を積み上げる、の2つを並行させる。

## 4-補. 将来のストア配信(App Store / Google Play)について

**今は着手しないが、判断材料として記録しておく。**

- **Google Playについて**: Android版は既存のiOSコードを移植するのではなく、**実質的に別プロジェクト**
  になる(Kotlin/Jetpack Compose、写真検知はMediaStoreのContentObserver、バックグラウンドは
  WorkManager)。「ついでに」出せるものではないため、検討する場合はiOS版とは独立した意思決定として
  扱うこと。
- **App Storeについて(2026-09-06、Apple公式Review Guidelinesを調査)**: このアプリの設計
  (写真ライブラリへのフルアクセス+新規写真を自動でTelegram Botへ転送するだけのシンプルな機能)は、
  以下のガイドラインで審査に引っかかるリスクが高いと判明:
  - **4.2 Minimum Functionality**: 単機能アプリは「単なるラッパー」と判定されやすい。
    "lasting entertainment value or adequate utility"が求められ、機能追加(フィルタリング・
    スケジュール設定・複数Bot対応等)なしでは却下されるリスクが高い。
  - **5.1.1(iii) Data Minimization**: 「新規写真のみ」が目的ならフルアクセスではなく限定フォトライブラリ
    アクセスや共有シートの使用が推奨されており、フルアクセス要求の正当性説明が必須。
  - **5.1.2(i) Data Use and Sharing**: Telegramへのデータ転送についてアプリ内でのユーザー明示的同意・
    プライバシーポリシーへの明記が必須。
  - **2.5.4 Background Services**: 「新規写真を自動転送」目的のバックグラウンド実行は、Appleが定める
    許可用途リスト(VoIP・音声再生・位置情報等)に該当せず、正当化の説明が必要。
  - **4.2.3(i) App Independence**: Telegram Bot設定が必須である以上「Telegramのラッパー」と
    見なされるリスクがあり、アプリ単体での付加価値の説明が必要。
  - 出典: Apple Developer公式Review Guidelines(developer.apple.com/app-store/review/guidelines/)
    および2026年時点の審査傾向解説記事複数(QAwerk, Volpis, OpenSpace Services等)。
- **結論**: 現状の設計のままではApp Store提出は却下リスクが高い。将来本気で目指すなら、単機能ラッパーの
  域を出る機能追加(検索・整理機能、複数送信先対応等)と、限定フォトライブラリアクセスへの切り替え検討、
  プライバシーポリシーページの用意が前提になる。**今はその投資をする段階ではないため着手しない。**

## 5. 競合・類似サービス調査(2026-09-06実施)

### 5-1. 「iPhone写真→Telegram自動転送」を謳うApp Store向けネイティブアプリ

**調査結果: 見つからなかった。** Web検索の範囲では、このアプリと同じポジション(PhotoKitで新規写真を
検知し、オンデバイスでTelegramへ自動送信するネイティブiOSアプリ)を取っている既存アプリは確認できず。
→ ニッチとして空いている可能性が高い(ただし調査範囲はWeb検索のみ、App Store内検索は未実施 - 要追加確認)。

### 5-2. 隣接する既存ソリューション(要注意・差別化ポイントに反映済み)

- **PhotoSync**(iOS定番の写真転送・バックアップアプリ、Dropbox/Google Drive/OneDrive/NAS/SMB/FTP等
  多数の送信先に対応)。**Telegramは送信先リストに含まれていない**(検索結果より)。多機能・高信頼だが
  Telegram特化ではないため、直接競合というより「まだ誰も埋めていない棚」の裏付けとして扱う。
- **IFTTT / Make.com の「写真が追加されたらTelegramへ送信」レシピ**: 元マニュアルのStep2案(ショート
  カット代替)と同種の発想が、既に他社の自動化プラットフォームとして存在する。
  **重要な差別化ポイント**: IFTTT/Makeは写真データが一度サードパーティのクラウドを経由する
  (=「開発者はおろか別会社にもデータが触れる」)。本アプリはオンデバイス処理でTelegramに直接送るため
  「経由するサーバーが一つもない」という点を明確に打ち出せる。また、それらの汎用連携では
  document/video形式の使い分け(原本画質保持)までは作り込まれていない可能性が高く、画質面でも優位。
- **TG-Photos**(GitHub, Python/Docker, MIT license): Telegramチャンネルを写真ストレージ化する
  自己ホスト型ツール。iOSアプリではなく、Docker運用+手動アップロード+タグ管理が主眼で、
  「新しい写真を自動検知して送る」体験は提供しない。技術者向けの別カテゴリ。

### 5-3. コンテンツ面(「Telegramを無制限クラウドとして使う」という切り口の既視感)

**重要な発見**: 英語圏では「Telegramを無制限無料クラウドストレージとして使う」という切り口自体は
複数のブログ・DEV Community記事で既に紹介済み(例: "I Built Unlimited Free Cloud Storage Using
Telegram"等)。**この「小ネタ」単体はもはや目新しくない。** 一方、日本語(note等)でのこの切り口の
記事は検索範囲では見当たらず、日本語圏コンテンツとしてはまだ空いている可能性がある。

→ **content戦略への反映**: 「Telegramが無制限なのを発見した」という語り口ではなく、
「その仕組みを自動化するiOSアプリを実際に作った」という開発・自動化の部分を主軸にする
(小ネタ自体の目新しさに頼らない)。note記事・動画台本の該当箇所は要調整(6節参照)。

## 6. SEO・検索性の方針(2026-09-06追加、README/note記事/動画/SNS投稿すべてに共通)

GitHubリポジトリの公開に合わせて「検索されて見つけてもらう」ことを意識する。README単体の話ではなく、
今後作る全コンテンツ(note記事タイトル、動画タイトル・概要欄、SNS投稿の冒頭)に共通するガイドライン。

### 6-1. 狙うキーワード(5節の競合調査に基づく)

- 主軸: 「iPhone 写真 Telegram 自動転送」「Telegram 写真 バックアップ」
- 周辺(課題側から来る検索): 「Google Photos 容量 代替」「iCloud 容量 いっぱい 対策」
  「写真 バックアップ 無制限」
- 日本語では「Telegramを無制限クラウードとして使う」という切り口の既存コンテンツが少ないため
  (5-3節)、この組み合わせでの検索需要はまだ競合が薄いと判断。

### 6-2. タイトル・見出しの付け方

- **核となるキーワードはタイトルの前半に置く。** 例: 「iPhoneの写真をTelegramへ自動バックアップ
  (容量無制限・オンデバイス処理)」(README H1で採用済み) — 後半に説明を続ける形は、検索結果の
  スニペットで前半だけ表示されても意味が通るようにするため。
- **感情フック(容量に疲れた、等)は保ちつつ、検索語彙を削らない。** 「Google Photosの有料化に疲れたので
  Telegramを無制限の写真バックアップ先にするアプリを作った」のようなタイトルは、感情フックと
  キーワードの両方を含んでいて理想形。
- GitHubリポジトリ自体の「description」フィールド(`gh repo edit --description`で変更可能)にも
  同じキーワードを含めておく(検索エンジン・GitHub内検索双方に効く)。README冒頭1〜2文が
  検索結果のスニペットに使われやすいため、ここにも核となるキーワード+要点を必ず入れる
  (README冒頭は本方針に沿って更新済み)。

### 6-3. 適用状況

- **反映済み**: README.mdのタイトル・冒頭文、GitHubリポジトリのdescription、note記事タイトルの確定、
  短編動画2本の投稿タイトル/概要欄。SNS投稿3パターンは元々冒頭にキーワードが来る構成だったため
  変更不要と判断。
